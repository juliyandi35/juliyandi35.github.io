# Juli Yandi Rahman — Portfolio

A scroll-driven, light "Scientific Atelier" portfolio built with Next.js (App
Router), TypeScript, Tailwind CSS, React Three Fiber, GSAP ScrollTrigger, and
Framer Motion. It presents mathematics, statistical research, public-sector
data systems, and applied AI work through 301 verified public GitHub
repositories. Scrolling does not move down the page so much as inward:
sections arrive out of the depth and pass behind you, and the journey ends
inside a 3D graph of the whole catalog.

## What this is built from

The repository catalog is **not** copied from a CSV export. Every one of the
301 repositories on `github.com/juliyandi35` already carries its own
classification in its GitHub description, in the form:

```
<Method family> [| <second method family>] | <Application(s)>
```

for example `Regresi, korelasi & ekonometrika | R / RStudio`, or
`Machine learning, AI & data mining | MCDM, optimasi & riset operasi | Python`
for a repository that spans two method families. `scripts/build-manifest.mjs`
fetches the public GitHub API for the account, parses that taxonomy, and
writes `data/manifest.json`. Two repositories on the account do not (yet)
carry this taxonomy in their description and are intentionally excluded from
the manifest, the same way a CSV pipeline would only keep rows marked
`Status = Selesai`.

Verified, at build time, from that data: **301 repositories, 13 method
families, and 16 distinct applications** (which appear in 19 combinations,
since a few projects use two tools together). No star counts, client outcomes,
accuracy scores, or years-of-experience figures are shown anywhere — they
are not derivable from public data, so they are not invented.

## Scrolling inward: the journey and the core

The page is not a column you scroll down — it is a distance you travel
inward. Every section is a layer suspended in front of the reader: it
arrives out of the depth, parks directly in front of them while they read
it, then rushes past and behind as they keep going. Behind all of it, the
core waits, and the last thing the journey reaches is the graph of every
project, filling the screen.

**The depth** (`components/Exploration/DepthLayer.tsx`) is CSS 3D, not WebGL.
Each section sits in its own `perspective` viewport and GSAP ScrollTrigger
drives it from `translateZ(-1150px)` and fully transparent, through a
**plateau** where it sits still at full opacity, to `translateZ(620px)` as it
passes behind the reader. The plateau is the part that makes this usable
rather than just a demo: without it a section would only be legible at the
single instant it crossed the centre of the viewport, which would make
something like the project atlas impossible to actually read.

Two things follow from doing this in CSS rather than in the 3D scene: the
sections stay in ordinary document flow (so any content length works, and
nothing is pinned or absolutely positioned), and the DOM stays a plain,
ordered document for screen readers, search engines, and keyboard users.
Each section has its own perspective viewport rather than sharing one on a
tall ancestor, because a single shared vanishing point sitting at the centre
of a multi-thousand-pixel container shears everything far from that centre.

**The core** (`components/Graph/GraphStage.tsx`) is a tall container with a
sticky, viewport-sized child — sticky rather than a GSAP pin, which needs no
pin-spacer and cannot desynchronise from the document height. Scrolling
through it maps to an `arrival` value: the first 45% is the approach (the
camera closes on the core and the backdrop deepens from porcelain to ink),
and the rest is dwell time, so the graph is not sliding out from under
anyone trying to click a node.

### The graph is a hierarchy, and it is computed, not stored

```
        root  ──▶  application  ──▶  project
      (1 core)    (16 tools used)  (301 repositories)
```

One core; one hub per application actually used across the catalog; every
repository hanging off the tool it was built with. The five repositories
that use two tools genuinely attach to both.

`lib/graph.ts` computes the whole layout from `data/manifest.json` at module
load: applications are spread evenly over a sphere by a golden-angle
(Fibonacci) distribution, and each application's projects form a small cloud
around it whose radius grows with the cube root of its project count, so node
density stays even whether a tool has one project or 112.

There is deliberately **no `data/graph.json`**. An earlier version baked a
force-directed layout into a committed file that had to be regenerated by
hand with Python and networkx — which meant the positions could silently
drift out of sync with the repository catalog. A closed-form radial layout is
cheap enough to compute at load, always matches the manifest exactly, and —
because every random-looking offset comes from a seeded PRNG — is identical
on the server and the client, so there is no hydration mismatch and nothing
to regenerate, ever. Refresh the manifest and the graph simply follows.

`lib/camera.ts` holds the framing maths as pure functions, so the approach
and the per-application framings can be unit-tested against the real graph
without a WebGL context — including the assertion that the arrival distance
is inside the graph's fitting distance, which is what "fills the screen"
means in numbers.

### Interaction, and its keyboard equivalent

Clicking a project node opens a small window with the repository's own name,
what it was built with, and a button straight through to GitHub
(`components/Graph/ProjectPopup.tsx`). Clicking an application hub — or any
of the floating buttons down the left of the stage
(`components/Graph/AppNav.tsx`) — flies the camera to that cluster and dims
the rest.

The canvas itself is decorative and `aria-hidden`. Everything it offers is
reachable without it: the application buttons are real `<button>`s with
`aria-pressed`, a focused application links straight into the project atlas
filtered to it, and the atlas — a searchable, paginated list of all 301
repositories, one of the layers on the way in — is the full keyboard and
screen-reader equivalent of clicking around the graph. Colour is never the
only channel; every application dot has its name in text beside it.

## Getting started

```bash
npm install
cp .env.example .env.local   # optional: add a GITHUB_TOKEN to refresh data/manifest.json
npm run dev                  # http://localhost:3000
```

`npm run dev` and `npm run build` both use the manifest already committed in
`data/manifest.json`; the live GitHub refresh only runs when you explicitly
call `npm run build:data` (or on `npm run build`, via the `prebuild` script),
and it silently falls back to the committed file if the GitHub API is
unreachable or rate-limited. Unauthenticated GitHub API requests are capped
at 60/hour, which is not enough to safely refresh ~300 repositories in one
run — set `GITHUB_TOKEN` in `.env.local` (a fine-grained, public-read-only
token) to raise that to 5,000/hour. The token is read only inside that one
Node script at build time: it is never bundled into client code, never
written back to `data/manifest.json`, and must never be committed.

## Commands

| Command | What it does |
| --- | --- |
| `npm run dev` | Local development server with hot reload |
| `npm run build:data` | Refresh `data/manifest.json` from the live GitHub API (falls back to cache on failure) |
| `npm run build` | Production build (runs `build:data` first, then `next build`) |
| `npm run start` | Serve the production build |
| `npm run lint` | ESLint (`next/core-web-vitals`) |
| `npm run typecheck` | `tsc --noEmit` |
| `npm run test` | Unit tests (Vitest): manifest parsing, atlas filtering, the graph's topology, and the camera framing maths |
| `npm run test:e2e` | Playwright smoke test: navigation, filtering, a repository link |

## Deploying

The project is a standard Next.js app and deploys to Vercel, Netlify, or any
Node hosting target without modification:

```bash
npm run build
npm run start
```

On Vercel: import the repository, leave the build command as `npm run build`,
and optionally add `GITHUB_TOKEN` as an environment variable so each
production build refreshes the manifest from live data.

## Fonts are self-hosted, not fetched from Google at build time

Space Grotesk and IBM Plex Mono ship as `.woff2` files under `public/fonts/`
and load via `next/font/local`, not `next/font/google`. This is a deliberate
fix, not a style preference: `next/font/google` fetches font files from
`fonts.googleapis.com`/`fonts.gstatic.com` during `next dev`/`next build`,
and on a network that blocks or interferes with that (a VPN, a corporate
proxy, a restricted BYOD network) the fetch fails — and on some Next.js
14.2.x versions that failure surfaces as an opaque, unhelpful
`at stringify (<anonymous>)` crash with a digest and no readable error
message, rather than a clear "couldn't reach Google Fonts" message. See
[vercel/next.js#52817](https://github.com/vercel/next.js/issues/52817) for
the same symptom reported by others. Self-hosting removes the network
dependency entirely — the exact same glyphs and weights load from disk every
time, offline or not.

## Accessibility and motion

- Skip link, semantic landmarks (`header`, `main`, sectioned `section`s,
  `footer`), and a logical heading hierarchy throughout.
- Every interactive element (nav, method tabs, atlas filters, accordions,
  pagination, the graph's application buttons) is a real
  `button`/`a`/`select`/`input`, reachable and operable by keyboard alone,
  with visible focus rings.
- `prefers-reduced-motion: reduce` removes the depth journey entirely — no
  ScrollTrigger is registered, the CSS falls back to untransformed sections,
  and the page becomes an ordinary vertical document. It also stops the
  camera's approach (the graph is simply there on arrival), stops its idle
  drift around the core, and — via the app-wide `<MotionConfig reducedMotion="user">`
  — turns every scroll-reveal into an instant, static one.
- Nothing invisible is ever focusable. The site navigation steps aside once
  the visitor is inside the core, and the graph's own controls do not exist
  for the keyboard until the core is actually reached; both use
  `visibility`, not opacity alone, so the hidden controls leave the tab order
  and the accessibility tree instead of becoming focus traps you cannot see.
- The project atlas announces its result count via an `aria-live` region, and
  the project popup takes focus when it opens and closes on Escape — it is
  deliberately not a modal, so the graph stays live behind it.
- Without WebGL the graph stage renders the same structure as plain links:
  every application, its project count, and a route into the filtered atlas.

## Known limitations of this build

- This project was authored in an environment without access to the npm
  registry, so it has **not** been through a real `next build` or a browser
  by the tool that wrote it. What was possible without `node_modules` was
  done: every `.ts`/`.tsx` file in `app/`, `components/`, `lib/`, `tests/`
  and `e2e/` was syntax- and JSX-checked with `esbuild`; the
  framework-independent modules (`lib/data.ts`, `lib/content.ts`,
  `lib/manifestParser.ts`, `lib/methodGlosses.ts`, `lib/graph.ts`,
  `lib/camera.ts`) were type-checked with `tsc --strict`; and `lib/graph.ts`
  and `lib/camera.ts` were also *executed* directly with Node against the
  real `data/manifest.json` — not merely statically analysed — to confirm the
  topology and the framing maths hold against real data (306
  application-project memberships, the five dual-tool projects attached to
  both hubs, every application framed from outside its own cluster and never
  inside another's, the arrival distance inside the graph's fitting
  distance). It follows standard, current APIs for Next.js 14, React Three
  Fiber, GSAP ScrollTrigger, and Framer Motion throughout — but please run
  `npm run typecheck`, `npm run lint`, and `npm run test` after your first
  `npm install`, and treat this section as the first thing to revisit if
  something doesn't compile.
- Every file importing a client-only library (framer-motion, React Three
  Fiber, three, GSAP, Phosphor icons) is checked by hand for a `"use client"`
  directive. That check is worth repeating after any edit: a missing client
  boundary is a Next.js App Router *runtime* rule, so neither `esbuild` nor
  `tsc` can catch it — and it is exactly what broke an earlier revision of
  this build, where every single page render failed with an opaque
  `at stringify (<anonymous>)` error simply because the root layout rendered
  `<MotionConfig>` directly instead of behind a client boundary.
- Per-repository README summaries and exact GitHub file-tree counts are not
  included: fetching them for 301 repositories individually is not possible
  within GitHub's unauthenticated rate limit, and no `GITHUB_TOKEN` was
  available while building this. `scripts/build-manifest.mjs` is already
  wired to accept one if you add it later.
- A Lighthouse pass (performance, accessibility, best practices, SEO) has
  not been run against a live deployment; do that once the site is deployed
  and treat any findings as follow-up polish, not a sign the architecture is
  wrong.
